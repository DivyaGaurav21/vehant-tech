# TrafficIQ

TrafficIQ is a smart-city traffic monitoring portfolio MVP. Camera video is recorded demo footage, and all traffic events are intended to be backend-generated simulation data—not live CCTV or real AI/computer-vision detections.

## Implemented milestones

- **Day 1:** responsive React dashboard foundation, six KPI values sourced through API service boundaries, analytics/alert panels, exactly nine camera cards, and camera detail routing. If backend data is unavailable, values stay blank rather than being fabricated.
- **Day 2:** Express/Mongoose backend, indexed schemas, nine-camera startup seeding, validated/paginated read APIs, MongoDB aggregation metrics, and backend-owned demo video configuration.
- **Day 3:** a single guarded backend scheduler, simulated vehicle detections and plausible violation records persisted in MongoDB, configurable event probabilities, start/stop/status API, dashboard controls, and generator/scheduler tests.
- **Day 4:** Socket.IO server/client events, post-persistence broadcasts for detections and violations, camera status-change broadcast support, a reconnecting single-connection React provider, dashboard REST refresh on connect/events, and transient violation toast alerts.
- **Day 5:** searchable, paginated violation and ANPR screens; persistent review status; bcrypt-hashed admin accounts; short-lived JWT login; and protected simulator/review operations.

## Project layout

- `frontend/` — Vite, React, JavaScript/JSX, React Router, Tailwind CSS, Axios, Recharts, Socket.IO Client, and Lucide.
- `backend/` — Express, Node.js JavaScript, MongoDB/Mongoose models and aggregation APIs, and YouTube demo video configuration.

## Run the frontend

```powershell
cd frontend
npm install
npm run dev
```

The frontend expects the agreed API envelope (`{ success, data, error?, meta? }`). Development requests default to `/api`; production builds default to `https://vehant-tech.onrender.com/api`. Override with `VITE_API_BASE_URL` if the backend URL changes. YouTube video IDs and embed URLs are supplied by the backend.

## Run the backend

Requirements: Node.js 20+ and a reachable MongoDB instance. Both applications use JavaScript; TypeScript and Zod are not required.

```powershell
cd backend
npm install
Copy-Item .env.example .env
# Configure MONGODB_URI, JWT_SECRET, ADMIN_EMAIL, and ADMIN_PASSWORD in .env
npm run dev
```

The backend runs directly on Node.js and does not require a TypeScript compilation step. Request query/body and environment values are validated by the backend's JavaScript validation helpers.

The API listens on port `4000` by default. It upserts exactly nine camera records on startup. The Vite development server proxies `/api` and `/socket.io` to `http://localhost:4000`.

For Vercel + Render deployments, set Render's `CLIENT_ORIGIN` to the exact Vercel site origin (for example, `https://your-app.vercel.app`; no trailing path). Separate multiple allowed origins with commas. The frontend defaults API and Socket.IO traffic to `https://vehant-tech.onrender.com`; if overriding `VITE_API_BASE_URL` or `VITE_SOCKET_URL` in Vercel, redeploy the frontend because Vite embeds these values at build time. YouTube feeds are loaded from `/api/traffic-videos`, so the backend origin and CORS setting must be correct for them to appear.

There are no committed/default admin credentials. For local development, choose an admin email and password and set `ADMIN_EMAIL` and `ADMIN_PASSWORD` in the backend's untracked `.env`; configure a private random `JWT_SECRET` of at least 32 characters. Use a unique development password (12–72 UTF-8 bytes); never copy production credentials into README, source, or frontend files. The configured password is stored only as a bcrypt hash. The seeded account is created/updated at backend startup; do not use development credentials in production. The login endpoint returns an eight-hour JWT, kept in browser session storage and sent as a bearer token for protected calls.

`GET /api/traffic-videos` returns exactly nine backend-configured YouTube traffic video assignments, one unique public video per existing camera ID, including its camera location and embed URL. The player autoplays muted, loops, and uses inline playback. If a video is unavailable or embedding is disabled, that camera shows an explicit fallback. These are recorded third-party demo videos, not live CCTV; simulated detection records remain generated by the backend simulation engine.

The simulator is **stopped by default**. Sign in at `/login` with the locally configured admin account to start or stop it from the dashboard, or call:

```powershell
Invoke-RestMethod -Method Post http://localhost:4000/api/demo/start
Invoke-RestMethod http://localhost:4000/api/demo/status
Invoke-RestMethod -Method Post http://localhost:4000/api/demo/stop
```

The start/stop requests above require a JWT bearer token when called directly.

`SIMULATION_INTERVAL_MS` sets the tick interval (default `3000`, minimum `250`). Violation probabilities are independently configurable with `SIM_NO_HELMET_PROBABILITY` (default `0.08`, motorcycles only), `SIM_RED_LIGHT_PROBABILITY` (default `0.025`), and `SIM_WRONG_SIDE_PROBABILITY` (default `0.012`). Every tick persists one `VEHICLE_DETECTED` event and zero or more associated violation records, all marked `SIMULATED`; reviewable violations start as `PENDING`. The scheduler prevents overlapping ticks, treats repeated starts/stops idempotently, reports failures in `/api/demo/status`, and is stopped during graceful server shutdown.

### API routes

- `GET /api/health`
- `GET /api/dashboard/summary` and `/api/dashboard/analytics`
- `GET /api/cameras`, `/api/cameras/:id`, `/api/cameras/:id/events`
- `GET /api/violations`, `/api/violations/:id`
- `PATCH /api/violations/:id/status` with `{ "reviewStatus": "REVIEWED" | "DISMISSED" }` (admin JWT required)
- `POST /api/auth/login` with `{ "email", "password" }`; `GET /api/auth/me` (admin JWT required)
- `GET /api/anpr` and `/api/events/recent`
- `GET /api/traffic-videos`
- `GET /api/demo/status`
- `POST /api/demo/start` and `/api/demo/stop` control the synthetic traffic scheduler (admin JWT required); `GET /api/demo/status` reports state and configured probabilities.

All list responses use the standard success envelope and pagination metadata. Dashboard summaries and analytics are computed with MongoDB aggregation pipelines; with a fresh database, event counts correctly start at zero. Event filters are validated and timestamps use UTC. Traffic event model indexes cover camera, timestamp, type, plate number, and review status. The violation and ANPR pages support plate, camera, date, and violation/review filters with backend pagination; all ANPR records are explicitly identified as simulated.

Socket.IO listens at `/socket.io`; clients reconnect automatically and fetch the REST APIs again after connecting/reconnecting. The simulator broadcasts `vehicle_detected` and, for each persisted violation, `new_violation` with camera location. Camera status changes are broadcast by the camera status service after the MongoDB update succeeds. All event payloads identify simulated data where applicable. These events are notifications; MongoDB-backed REST APIs remain the source of truth.
